## Input #1：长护险标准目录体系

首先我们的系统要支持长护险业务（为主），也可能需要管理其他业务。

长护险业务是有国家标准和地方标准的。国家标准是基础，地方标准可能有不同。比如国家标准的服务项目是36条，杭州市有41条。

所有的上门服务，都是在标准项目里选择若干项进行服务的。

我上传了文档"杭州市长护险要求……"和"国家医疗保障局……"，里面就记录了杭州政府和国家医保局分别定义的标准服务清单。

杭州的清单只是针对杭州有效。其他地区，可能使用国家标准，也可能使用地方性的标准。

因此，系统内应该有一个静态数据的维护，去维护几套不同的标准目录。每套标准目录里都要定义一个数据结构，比如标准名称、服务项目名称、服务项目大类、单次服务参考时间、服务频次等等。

### 参考文档

- **国家标准**：《国家长期护理保险服务项目目录（试行）》（医保发〔2025〕24号），36项，分为生活照护类（20项）和医疗护理类（16项）。数据结构含：序号、项目代码（18位）、项目类别、项目名称、项目内涵、服务要点、推荐服务人员、推荐服务时长。
- **杭州标准**：《杭州市长期护理保险护理服务管理办法（试行）》（杭医保〔2024〕29号），41项，分为六大类：清洁卫生类（1-15）、营养摄取类（16-18）、排泄护理类（19-26）、移动舒适和安全护理类（27-37）、生命体征观察与护理类（38-39）、用药指导类（40-41）。数据结构含：项目编号、项目内容（大类+子项）、单次服务参考时间（分钟）、服务频次。
- **杭州附件2**：护理服务计划样表，含服务对象基本信息（姓名、性别、身份证号、现住地址、重度失能等级、联系人、定点长护服务机构）+ 护理服务项目列表（项目编号、项目名称、服务时长、服务标准和要求、服务频次）。
- **杭州附件3**：护理服务供给规范，6张表，每个服务项目含"基本服务要求"和"注意事项"。

## Input #2：业务初始化阶段——制定"服务包"

我前面讲的是长护险服务的内容。后面讲金色年华实际进行长护险服务时的业务流程（也是一般养老机构做长护的流程）。

首先会有一个"业务初始化"阶段。（这个"业务初始化"是我自己为了方便叙述定义的词，不是真实业务的概念）

比如金色年华有一个余杭站点，那么余杭站点覆盖范围内可能存在一些失能老人（长护险目前只覆盖失能老人）。

金色年华的销售会找到这些老人，帮助他们申请长护险资格。成功申请以后，护士会对老人进行身体评估，然后给出一个"长护险服务计划"（俗称"服务包"，我后面可能会说服务包，你要知道正式说法是服务计划。）。

这个"长护险服务计划"的格式和内容是有明确定义的，你可以看《杭州市长护险要求……》那个文档。

"长护险服务计划"的核心概念是定义这个老人可以做哪些项目，频次是多少。

然后，站点会给老人分配一名护工。（老人会固定一个"常用的"或者"默认的"护工；一个护工可以对应服务多名老人，最多不超过8名。护工和老人的对应关系的管理需要体现在系统里。）

然后，护工拿到老人的"长护险服务计划"表，也就知道了未来服务的大致框架。

## Input #3：服务资质问题

长护险站点有两类人员，护工和护士。两者的核心区别是持有的资质不同。

护工可以做护理类的项目。护士可以做医疗类的项目。

因此，从系统管理的角度，我明确要求：需要以"资质"作为一个核心的逻辑来串联。

比如，长护险规定的某一项服务A，这个服务会定义需要K资质。然后站点里的人员，比如小王是有K资质的。那么，系统就会认为，小王是可以做服务A的。这个是硬性约束，没有资质就不能做对应的服务。

因此，有一些推论：

1）尽管在前面的叙述中，我说"站点会给老人分配一名护工"，但这个不是"硬约束"。因为，有时候会可能出现护工请假不在的情况，需要其他护工来代班。因此，站点给老人分配的护工可以作为一个for information的信息，但不是逻辑上的硬约束。
2）虽然站点有明确区分护士、护工，但系统层面我们不做role的定义。我们只用"资质"去判断"谁可以做什么服务"、"谁不可以做什么服务"。

## Input #4：服务排班问题

前面我讲了"服务包"的概念。服务包，通俗点说，其实就是一个"套餐"，定义了老人可以享受哪些服务项目。

现在我需要引入一个概念，叫做服务排班。因为在现实中，护工/护士肯定是需要有一个时间上的规划的，比如本周7天，服务哪几个老人，约了几点……

对于此类上门服务来说，我们需要从宏观管理角度去对排班进行管理，进而对站点的运营效率、服务人员的时间效率进行管理。

为什么排班那么重要，两个角度：
第一是从管理角度，排班的合理性就是效率，效率就是净利率。
第二个是从医保的要求角度，医保对长护的服务有很多约束性的要求：1. 一个护工最多服务8个老人。2. 每个老人每个月有25小时服务额度。3. 额度过期作废。如果作废，比如老人本月只使用了15小时，还有10小时没有用，那么下个月也不会补回来给老人，同时服务人员和金色年华机构也拿不到对应的医保拨付款项，对双方都是白白浪费。4. 医保要求每周都做上门服务，如果在一个自然周之内没有上门，那么这一周的拨付额度就会作废。比如说，一个老人一个月25小时，每小时按60元/小时的标准拨付，平均到每周6小时左右、360元，如果本周没有上门，那么这360元是不会拨付的，会从本月的总额度里直接硬性扣减，哪怕另外三周多做几次也没有用。5. 医保可能会要求每次上门在1-2小时之间，不能低于1小时，也不能超过2小时。这个要求可能随着地区不同而不同。我建议你把每个地区的长护险目录、站点的地区属性、医保的隐形约束/规则做一个关联。比如说余杭站点在排期时，除了使用杭州市的长护险服务目录以外，还会check是否满足杭州当地的隐性约束。这个隐形约束/规则应该有一个地方来管理，比如attach在长护险服务目录的数据结构下。

在实际工作中，我希望服务排班可以实现几个功能特性：

1）服务人员本人可以基于所有的服务对象（老人）以及他们的服务包的信息，借助AI助手生成排班。
2）所有的排班都可以在calendar形式中查看。
3）服务人员可以在手机app中查看calendar。
4）服务本人人员以及站点运营人员（站点的operator角色，这里是系统role的概念）可以通过AI助手去调整服务排班，包括recursive的排班，或者针对某次服务的排班。
5）排班应该包括老人/服务对象、上门时间、预估服务项目。
6）服务人员本人以及站点运营人员能够基于服务排班，（可能借助AI助手的帮助），来评估、优化排班的合理性。
7）在系统内可以看到某一个服务人员（比如某位护工）、针对某位服务对象（比如某位老人）的排班。
8）在系统设计上，尽可能基于现有的相关数据结构去设计。如果你觉得现有数据结构无法满足，需要改动，要明确告诉我。

## Input #5：服务人员上门流程

### 5.1 目前金色年华老系统的做法

目前金色年华使用一个手机app，护工必须操作app，并完成上门服务。具体流程：

1）护工在上门之前，要在app里选择一位具体的要服务的老人，比如李大爷。
2）护工要选择今天做哪几项服务。是在服务包的限定范围内勾选。勾选以后app界面会给出总共选了几项、工时加起来是多少。如果护工觉得没有问题，就点击"接受服务"按钮。
3）随后，会跳出一个确认界面。包括：服务对象/项目/工时的信息展示、GPS定位确认、信标连接确认。GPS和信标连接都需要手动触发来verify。GPS就是看护工手机定位是否匹配李大爷在系统内登记的住址。信标是金色年华提前在李大爷家里安装的蓝牙装置，和手机连接后确认护工确实在李大爷家里。两个都verify成功，界面点亮"开始服务"按钮。
4）过程中，app一般不会做什么。但只有一个情况例外，就是如果系统后台侧发起视频飞检，那么护工就要在app里接受一个视频通话，确认服务是否正常。目前，这个飞检只是随机抽查的逻辑，因为金色年华现有系统无法识别服务是否有任何异常或者可疑迹象。飞检完毕后，系统内会保留飞检记录。
5）完成服务后，护工需要点击"结束服务"。从"开始"到"结束"的时间就是实际工时。然后，护工需要上传一张现场照片（拍摄老人）到app。
6）由此，系统后台会有一条完整的上门服务记录。金色年华会基于这个记录做内部管理、医保财务核对等活动。

### 5.2 我们的系统的考虑

1）首先，老的能力，都要支持。
2）老系统有流程上的问题需要解决。比如：护工需要在服务开始前勾选服务项目，再开始服务，这个在开始后不能更改。但这不符合现实需求，因为老人有可能在服务中有新的需求出现，导致服务项目需要改动。我希望我们的设计可以提供灵活性，比如服务之前可以先预估一个计划，但服务结束时可以再次确认完成的项目，并且和实际发生的工时做核对，如果符合工时则允许确认服务结束。
3）我们的系统需要支持多维度交叉验证能力，包括：GPS、信标、录音（录音本身以及声纹检测）、毫米波雷达、视频飞检。
4）其中GPS、信标、录音、毫米波雷达贯穿全程。GPS要全程打点，以防护工中途离开服务地点。
5）其中，录音+毫米波雷达是老方案没有使用，但是在我们新系统里要支持的核心能力。护工在服务之前，需要把毫米波雷达放在床前，让雷达可以覆盖床前的区域。开始任务后，app就进入"服务模式"。此时，护工可以看到，本次服务的基本信息。并且，界面显示所有"实时运行"的监控项，比如毫米波雷达实时数据、录音状态和实时日志、实时引导督导信息。毫米波雷达是和护工身份绑定的小型可移动设备。系统里需要管理护工与设备的绑定关系。这样，系统就会知道，这个毫米波雷达就是属于护工A的。录音状态和实时日志，指的是服务开始后，就会默认录音，同时app界面返回录音的状态（比如"正在录音+绿色圆点"），以及推送的文本日志（由ASR处理生成）。实时引导督导信息，指的是系统后台的AI agent，会根据雷达信息+录音信息，结合预设的AI引导/督导策略，对发现的问题或需要引导的流程进行提示。这个提示在被触发后，会出现在这个app显示区域，同时通过TTS生成语音外放出来。

## Input #6：服务在后台的展示和管理

进一步，我们需要考虑在系统后台，每次的服务是如何被展示和管理的。我的几点要求：

1）我们需要考虑admin页面/operator页面的tab设计。
2）我们需要考虑正在进行的服务如何展示。这个一定需要，很重要，体现了实时监控监督的能力。
3）需要考虑已经完成的服务如何展示。
4）需要考虑排班和服务之间的耦合关系。比如我觉得，可能的合理方案是，两者不强制耦合，因为可能出现临时的需求。但是在服务结束之后，会展示这次服务是否匹配了服务之前的排班计划。从宏观上，站点/总部可以分析排班的合理性。但我的思路不一定正确，也许应该follow排班，就好像美团/快递的管理一样，外卖员/快递员必须follow订单的信息来完成任务。这块我需要你给我一些建议。我希望能满足管理/效率提升的设计需求，也能照顾到实际中会发生的一些难点，比如上门的灵活性，和很多护工本身也是文化程度较低的老人的事实。
5）对于服务，无论进行中还是已完成，都要强调我们的"多维度证据链"概念，要突出证据是否匹配符合。
6）也就是说，两个超级重点。一个是真实性的核查（证据链），一个是管理/效率问题（护工时间最大化利用、老人额度最大化利用）。

## 补充 Input #12：长者页面修正

1）"资格"固定显示"长护险"，目前就一种。
2）"服务计划"和"服务排班"理解有混淆需要修正。服务计划不是服务排班。服务计划是在录入老人信息时就会预先确定好，这个老人在长护险里面可以使用哪些服务项目。参考附件里的服务计划标准格式。它是一个相对静态的、约束性的信息。而服务排班是排班，在calendar里显示。因此，在一个老人的具体信息中，"服务计划"和"服务排班"需要独立的tab去管理。

5）"服务历史"tab保留。
6）"AI洞察"tab不要保留。

补充：

- 服务排班使用统一的calendar view，有日/周/月视图切换，可以查看其他时间段。

## 补充 Input #11：老人失能等级核查

针对所有的服务，监管（包括集团总部和医保审计角度）都想要能看到，除了监督服务人员的行为以外，也要监督老人。

为什么要监督老人？要防止老人在失能等级上作弊。因此，我们通过毫米波雷达同时观察服务人员的行为和老人的行为。

具体来说：
1）对于每一次服务，要针对老人失能需要做核查，并给出结果。这是一个单独的核查项目，和服务人员的"多维度交叉核查"并列存在。
2）失能等级的具体数据来源于毫米波雷达的数据，主要基于服务期间老人是否无法移动来判断。
3）在UI上，毫米波雷达的数据可以体现为一个热力图，即老人的活动位置，和护工的活动位置。类似于足球分析的球员活动区域热力图。当然，热力图还有底层更基础的数据，就是一个随着时间推移打点的任务相对活动位置动态视图，类似于一个小视频，可以拖动进度条查看服务全程两个人的相对位置变化。你可以在UI上给出相应的内容。
4）auditor的页面也是如此，一定要独立地、明显地给出针对老人的核查结果。把针对老人的核查，和针对护工的核查，放到同样的重要性上去。

## 0604 版本偏差说明

0604 版本中得出了"废弃排班"的结论，这是一个重大偏差。原因是：当时我说"护工和老人自行约定时间，系统不做预排班"，是因为金色年华目前没有做排班管理。但深入了解后发现，金色年华只是因为没有能力支持排班管理才没有做，并不是理论上就"不应该做"。

排班是核心管理工具，直接影响运营效率和医保拨付。医保有多重硬约束（8人上限、25小时/月额度、每周必须上门、单次1-2小时等），不做排班管理就无法最大化利用这些额度。

**教训**：当用户说"现在没有做X"时，要追问"是因为不需要X，还是因为没能力做X"，而不是直接得出"X不需要"的结论。
