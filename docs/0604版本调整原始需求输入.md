## Input #1：长护险标准目录体系

首先我们的系统要支持长护险业务（为主），也可能需要管理其他业务。

长护险业务是有国家标准和地方标准的。国家标准是基础，地方标准可能有不同。比如国家标准的服务项目是36条，杭州市有41条。

所有的上门服务，都是在标准项目里选择若干项进行服务的。

我上传了文档"杭州市长护险要求……"和"国家医疗保障局……"，里面就记录了杭州政府和国家医保局分别定义的标准服务清单。

杭州的清单只是针对杭州有效。其他地区，可能使用国家标准，也可能使用地方性的标准。

因此，系统内应该有一个静态数据的维护，去维护几套不同的标准目录。每套标准目录里都要定义一个数据结构，比如标准名称、服务项目名称、服务项目大类、单次服务参考时间、服务频次等等。

### 参考文档

- **国家标准**：《国家长期护理保险服务项目目录（试行）》（医保发〔2025〕24号），36项，分为生活照护类（20项）和医疗护理类（16项）。数据结构含：序号、项目代码（18位）、项目类别、项目名称、项目内涵、服务要点、推荐服务人员、推荐服务时长。
- **杭州标准**：《杭州市长期护理保险护理服务管理办法（试行）》（杭医保〔2024〕29号），41项，分为六大类：清洁卫生类（1-15）、营养摄取类（16-18）、排泄护理类（19-26）、移动舒适和安全护理类（27-37）、生命体征观察与护理类（38-39）、用药指导类（40-41）。数据结构含：项目编号、项目内容（大类+子项）、单次服务参考时间（分钟）、服务频次。
- **杭州附件2**：护理服务计划样表，含服务对象基本信息（姓名、性别、身份证号、现住地址、重度失能等级、联系人、定点长护服务机构）+ 护理服务项目列表（项目编号、项目名称、服务时长、服务标准和要求、服务频次）。
- **杭州附件3**：护理服务供给规范，6张表，每个服务项目含"基本服务要求"和"注意事项"。

## Input #2：业务初始化阶段

我前面讲的是长护险服务的内容。后面讲金色年华实际进行长护险服务时的业务流程。

首先会有一个"业务初始化"阶段。（这个"业务初始化"是我自己为了方便叙述定义的词，不是真实业务的概念）

比如金色年华有一个余杭站点，那么余杭站点覆盖范围内可能存在一些失能老人（长护险目前只覆盖失能老人）。

金色年华的销售会找到这些老人，帮助他们申请长护险资格。成功申请以后，护士会对老人进行身体评估，然后给出一个"长护险服务计划"。

这个"长护险服务计划"的格式和内容是有明确定义的，你可以看《杭州市长护险要求……》那个文档。

"长护险服务计划"的核心概念是定义这个老人可以做哪些项目，频次是多少。

然后，站点会给老人分配一名护工。（老人会固定一个护工；一个护工可以对应服务多名老人，最多不超过8名。护工和老人的对应关系的管理需要体现在系统里。）

然后，护工拿到老人的"长护险服务计划"表，也就知道了未来服务的大致框架。

## Input #3：日常服务流程 — 上门准备与工具

然后我在说日常/常规的服务流程。

首先，护工会和老人进行电话联系，或者在线下约定好，下一次上门的时间。这个时间是看老人和护工商量的，系统不会提前做约束和安排。

假定护工A和老人B商量好今天下午3点上门，那么护工就会在3点上门。

上门时，护工会携带两个东西：第一是自己的手机，第二是毫米波雷达设备。

自己的手机里有两个app/小程序：泰照护app、金色年华app（也就是我们所谓的服务人员用的移动端H5页面）。

泰照护是医保局使用的服务记录app，金色年华app是金色年华自己用于内部管理的。护工需要同时使用两个app；这两个app目前没有互通的机制。

金色年华app需要覆盖泰照护的所有功能，加上我们想要加入的额外功能。

## Input #4：服务人员 App 流程

继续讲app所需要支持的流程：

1）护工的app是需要登陆的。用户名密码应当在站点运营dashboard中进行管理。

2）登陆后，护工可以看到自己可以服务的老人。这些老人是之前固定分配给该护工的。

3）护工选择老人，比如老人B。页面会弹出对应老人B的基本信息（姓名、地址、电话）以及服务计划所约束的服务项目，服务项目显示为一个列表，包含服务项目、要求的频次、参考工时。比如："失禁护理-10分钟-必要时"。如果护工认为今天需要做这个项目，就勾选这个项目，可以勾选多个。界面会统计出已选项目有几项、合计工时是多少。护工确认没问题，再点击"接受任务"。

> 参考截图：泰照护 App "任务详情"页面 — 显示参保人姓名/地址/电话 + 服务项目勾选列表（按大类分组，含参考工时和频次）+ 底部统计（已选项目数、合计工时）+ "接受任务"按钮。

4）同时，护工在服务之前，需要把毫米波雷达放在床前，让雷达可以覆盖床前的区域。开始任务后，app就进入"服务模式"。此时，护工可以看到，本次服务的基本信息。并且，界面显示所有"实时运行"的监控项，比如毫米波雷达实时数据、录音状态和实时日志、实时引导督导信息。

5）其中，毫米波雷达是和护工身份绑定的小型可移动设备。系统里需要管理护工与设备的绑定关系。这样，系统就会知道，这个毫米波雷达就是属于护工A的。

6）录音状态和实时日志，指的是服务开始后，就会默认录音，同时app界面返回录音的状态（比如"正在录音+绿色圆点"），以及推送的文本日志（由ASR处理生成）。

7）实时引导督导信息，指的是系统后台的AI agent，会根据雷达信息+录音信息，结合预设的AI引导/督导策略，对发现的问题或需要引导的流程进行提示。这个提示在被触发后，会出现在这个app显示区域，同时通过TTS生成语音外放出来。

## Input #5：任务确认流程补充 — GPS + 蓝牙星标

有一些我遗漏的点：

护工在点击"接受任务"以后，任务并不会立即开始。而是又弹出一个页面，核对GPS和星标。

GPS就是系统会核对护工当时的定位和老人地址是否一致。

星标是一个安装在老人家中的蓝牙设备，用于核对护工是否真的到了老人家中。

两个核对上，服务就可以开始。护工再点击"开始服务"。就开始了。

## Input #6：站点人员角色体系

再说一下站点里的人员。主要有三类：护士、护工、销售。

护士要负责老人的评估，以及做医疗类的服务。护士不对应特定老人，而是按需上门。服务项目里面医疗类的只能护士做，不能护工做。护士也会做一些管理类的工作，比如回访、护理质量控制。

护工会有对应的特定的老人，不超过8个。

销售也是站点人员，主要工作是寻找符合长护险条件的老人，推动签约。

因此，系统内需要有一个权限的对应，比如某些服务项目需要护士资质，护工就不能做。三个role需要区分。

还有一个重大调整，是我想要加入一个全新的dashboard以及用户类型，即面向医保局的dashboard。其功能是帮助医保局监督、审计所有的长护险服务。大致规划如下：

功能说明：

1）"总览仪表盘"全市核心指标（服务总量、经费支出、机构数量、覆盖老人数），跨机构质量排行和异常预警汇总。

2）"机构管理"定点机构列表，基本信息、服务规模、质量评分/评级。点击下钻到单个机构的详细指标。

3）"服务审计"按条件检索任意一次服务，查看完整审计视图（六重证据链+AI评估+关联回访/反馈）。支持随机抽查模式。

4）"异常与预警"AI 自动标记的异常服务列表，分类分级。跨服务模式识别（系统性异常检测）。处理流程追踪（待核实→已核实→已处理）。

5）"标准与合规"医保局发布的官方标准，各机构的执行合规率。跨机构横向对比同一标准的执行情况。

6）"质量趋势"跨机构多维度质量对比，单机构质量趋势（改善/恶化），机构自动评级（A/B/C/D）。

## Design Spec Review 修正记录（mexy 补充输入）

### 修正 R1：角色体系 — 用"资质"解耦，不改 worker 数据结构

不应该轻易修改worker的系统定义和数据结构。应该建立的业务逻辑是：

1）一个老人在系统里有一个服务计划。

2）服务计划本质上是一个类似于"套餐"定义，比如老人可以做哪几项服务。

3）对于每一项服务，应该有一个"资质"的定义。一个服务可以对应多个"资质"。比如，"药物管理"需要"护士"资质。

4）从系统设计上，我们再给站点的所有worker去匹配"资质"。一个worker可以匹配多个"资质"。

5）因此，"谁可以服务谁"是由"资质"这个字段去约束的。一个老人有一个服务计划，服务计划里"药物管理"这一项服务，如果定义了资质要求是"护士"，那么所有拥有"护士"资质的worker理论上就可以给他服务。

6）之前说，在实际管理中，每个老人会分配一个固定的护理员/护工，其实是一个管理需求，不是底层数据结构需求。完全可以用额外的方式去约束。比如在护工的app里，管理"常用服务对象"为他负责的那几个老人就可以了。但理论上只要资质能对上，就可以选择老人进行服务。这样，也可以应对偶尔因为护工请假导致需要其他护工临时应急的情况。

### 修正 R2：服务计划常用服务人员 + App 常用服务对象 — 均为软关联

服务计划可以定义一个常用服务人员，但也可以不定义。这个只是for information。

对于护工，他可以在app里设置"常用服务对象"，这样app里每次都是出现分配给他的那些老人。

但是以上，都不是写死的东西，不存在hardcode或者硬约束的逻辑。

### 修正 R3：缺失环节回复

G1 标准目录的管理入口在哪？admin 页还是独立模块？--》在 admin 下新增「服务目录管理」tab。然后匹配「服务标准管理」（也就是现在的标准规范管理）。

G2 销售角色在 Dashboard 和 App 中具体能做什么？--》按照刚才讨论的，不需要定义销售/护士/护工角色了。

G3 护士的 App 流程和护工是否完全一致？App首页逻辑完全一致。如果你觉得有疑问，告诉我。

G4 服务计划的审批流程？谁创建、谁审批？--》站点运营创建和确认即可。因为站点运营可能就是护士。这里不需要搞复杂。

G5 录音来源如何识别？手机录音 vs 雷达录音 vs 工牌录音 需要在 ServiceSession 中标记 audioSource --》可以。我们初期只考虑手机，这里只是留一个口子。

G6 AI 督导策略从哪里配置？--〉admin页面的标准管理tab本来就有督导策略配置。只是在新的逻辑下，会有「服务目录管理」tab、「服务标准管理」tab。定义了服务目录以后，就可以去定义对应服务的标准（SOP、引导策略、督导策略、报告策略）。不过我认为这里真正的问题是，原来的AI策略配置，只是基于录音的，其实以后应该把其他因素，比如GPS、雷达数据纳入考虑。但现在的架构是不支持的。这块你可以写一个待定事项，需要架构师考虑。

G7 医保局用户如何登录？独立账号体系还是共用？建议共用 auth，新增 role 判断跳转 --》现在可以先共用auth。

G8 六重证据链中"声纹"如何采集和验证？服务开始时自动采集 vs 手动触发？--》不是在服务中采集。是在录入员工/worker信息的时候，就有一个采集声纹的环节，因为采集声纹的目的是身份匹配，所以要在最开始做。这样后面服务中，如果发现不匹配，可以显示预警/异常。

### 修正 R4：医保局审计入口 scope 收缩

对于医保局的dashboard，我想要调整一下思路。原先的设计稍微有点激进，我想把它作为一个医保局管理当地各个机构的平台。但我觉得这样不妥，我想收缩scope，把它仅作为医保局用来audit和抽查金色年华机构所有服务记录的一个入口（"审计核查入口"而不是"管理平台"的概念）。

因此，tab和功能可以做大幅度简化。核心是：针对所有已完成服务的审计功能（重点关注所有维度的交叉检查项目是否都通过，是否有异常，是否有严重违规行为）。然后首页再做一个overview页面，把统计性的信息加入，比如今日完成、异常与预警（基于六维度审计出现的不匹配项目）、质量趋势。

简化为 2 个 Tab：服务总览 + 服务核查。原设计的「机构管理」「异常与预警」「标准与合规」「质量趋势」4 个独立 Tab 移除。
